## BLOCKING

### B1. Overlapping polls on the same task: no in-flight guard anywhere
- Where: `app/components/Ledger.tsx:93` (`setInterval(tick, 3000)`; `tick` is async and never awaited, so a new tick starts while the previous one is still awaiting `/poll`), `lib/runner.ts:149-159` (`poll` reads the whole row, awaits Fo, then `applyReply` writes the whole row), `lib/runner.ts:177` (`alreadyAnswered` is read from the stale in-memory task), `lib/runner.ts:243` (`reaskCount` likewise), `lib/store.ts updateTask` (last writer wins; no version check).
- Scenario (live Fo): the contract (§8) says `get_fo_reply` blocks up to 40 s. Every 3 s the client fires another `/poll` for the same working task, so up to ~13 `get_fo_reply` calls are in flight at once. Each one logs a `get_fo_reply` trace event (the drawer and the exported JSONL for form item F fill with duplicates), the last writer overwrites `foProgress` so progress lines are lost, and when two replies both say `waiting_for_user`, both see `alreadyAnswered=false` and both call `ask_fo("Yes, go ahead.")` (the confirmation is answered twice). Two concurrent `complete` replies each run `check`, each see `reaskCount=0`, and Fo is re-asked twice.
- Reproduction: not reproducible on the fake (its replies return in microseconds, so the window never opens; three concurrent `POST /api/tasks/<id>/poll` on :3101 came out clean). It follows directly from the code, and it will happen in the live take whenever a `get_fo_reply` takes longer than 3 s.
- Fix shape: a per-task in-flight map in the poll route or runner (`Map<taskId, Promise<Task>>`, return the pending promise to a second caller), and in `Ledger.tsx` skip the tick while the previous one has not resolved.

### B2. `ask_fo` is retried automatically every 3 s after a dispatch failure
- Where: `lib/runner.ts:149` (`if (task.status === 'allowed' && !task.dispatchedAt) return dispatch(...)`), `lib/runner.ts:128-131` (a thrown `askFo` leaves status `allowed`, `dispatchedAt` null), `lib/view.ts:37` (`ACTIVE_STATUSES` includes `allowed`), `app/components/Ledger.tsx:84-93` (every active task is polled every 3 s).
- Scenario: Fo accepts the errand but the HTTP/SSE response is lost (timeout, drop) so `askFo` throws. The row shows "Fo did not accept the task" with a "Try sending again" button, but the 3 s loop already calls `/poll`, which calls `dispatch`, which calls `ask_fo` again, and again every 3 s until Fo answers. ARCHITECTURE.md "Failure boundaries" says "No retries on ask_fo (a second ask would be a second errand)"; the code does the opposite. While Fo is down this also writes an `error` trace event every 3 s per task.
- Reproduction: by code path only (the fake `ask_fo` never throws). To see it with the fake, make `FoClient.askFo` reject once and watch the trace: `ask_fo failed` events every 3 s.
- Fix shape: do not auto-poll `allowed` tasks that carry an error (manual retry only), or record `dispatchAttempts` and stop after one.

### B3. README run instructions and the OAuth redirect URIs disagree on the port
- Where: `README.md` "Run it" (`npm run dev -- -p 3100`, `http://localhost:3100/connect`), `.env.example:4` (`APP_URL=http://localhost:3000`), `.env.example:12` and `app/connect/page.tsx:86` (hard-coded `http://localhost:3000/api/google/callback`), `lib/fo/client.ts foOptionsFromEnv` and `lib/google.ts googleFromEnv` (redirect URL built from `APP_URL`).
- Scenario: a judge or user copies `.env.example` to `.env.local` as told, runs on 3100 as told, clicks Connect Fo or Connect Google Calendar: Wajo and Google redirect to `http://localhost:3000/api/...callback`, where nothing listens. The /connect hint tells them to register the :3000 URI even when APP_URL says otherwise.
- Fix shape: one port everywhere (README, .env.example, /connect copy), or print the redirect URI from `APP_URL` on /connect instead of a literal.
